记忆配置

记忆类型

四种记忆类型

  1. 工作记忆（WorkingMemory）：负责存储当前对话会话中的临时信息。采用内存（列表）进行存储，
  2. 情景记忆（EpisodicMemory）：负责存储事件的完整性和时间序列关系。采用 SQLite+Qdrant 的混合存储方案，SQLite负责结构化数据的存储和复杂查询，Qdrant负责高效的向量检索。
  3. 语义记忆（SemanticMemory）：负责存储抽象的概念、规则和知识。采用了Neo4j图数据库和Qdrant向量数据库的混合架构，这种设计让系统既能进行快速的语义检索，又能利用知识图谱进行复杂的关系推理。
  4. 感知记忆（PerceptualMemory）：负责文本、图像、音频等多种模态的数据存储和检索。它采用了模态分离的存储策略，为不同模态的数据创建独立的向量集合。

对于一个记忆，其所需的动作如下

  • 添加记忆
  • 检索记忆
  • 更新记忆
  • 删除记忆
  • 判断记忆是否存在
  • 清空记忆
  • 获取记忆统计信息

故这里创建一个记忆基类 BaseMemory，用于定义所有记忆的基础动作和属性

遗忘记忆

检索记忆

情景记忆的检索实现展现了复杂的多因素评分机制。它不仅考虑了语义相似度，还加入了时间近因性的考量，最终通过重要性权重进行调节。评分公式为：(向量相似度 × 0.8 + 时间近因性 × 0.2) × (0.8 + 重要性 × 0.4)，确保检索结果既语义相关又时间相关。

语义记忆和感知记忆的总结（ai）

基于提供的代码和说明文档，以下是对语义记忆和感知记忆的分点总结：

一、 语义记忆 (Semantic Memory)
1. 是什么？

语义记忆是记忆系统中最复杂、最抽象的部分。它不只是存储孤立的数据，而是负责存储抽象的概念、规则、事实知识以及它们之间的关联。它的核心在于“知识的结构化”和“推理能力”。

2. 是怎么做的？
  • 混合架构设计： 采用了“图数据库 (Neo4j)” + “向量数据库 (Qdrant)”的结合。
    • Qdrant：负责通过向量相似度进行快速的语义匹配。
    • Neo4j：负责存储实体（Entities）和关系（Relations），构建知识图谱。
  • 存储流程 (Add)：
    1. 嵌入：将文本转化为向量。
    2. 提取：利用NLP技术从文本中自动提取实体和关系。
    3. 入库：将实体/关系存入图数据库，将向量和元数据存入向量数据库。
  • 检索流程 (Retrieve)：
    • 执行混合检索：同时进行向量检索（找相似）和图检索（找关联）。
    • 混合排序算法：
      • 公式：(向量相似度 × 0.7 + 图相似度 × 0.3) × (0.8 + 重要性权重 × 0.4)。
      • 设计逻辑：以语义相似度为主（0.7），关系推理为辅（0.3），并根据记忆的重要性（Importance）进行加权调整。
3. 有什么用？
  • 深度理解：不仅能匹配字面意思，还能理解概念间的深层联系。
  • 逻辑推理：通过知识图谱发现隐含的关联（例如：A导致B，B导致C，推导出A与C有关）。
  • 精准问答：在回答复杂问题时提供有结构支撑的事实依据。
4. 举个例子

场景：用户输入“爱因斯坦提出了相对论”。

  • 系统动作：
    • 提取实体：“爱因斯坦”、“相对论”。
    • 提取关系：“提出”。
    • 存入图谱：(爱因斯坦) --[提出]–> (相对论)。
  • 后续应用：当用户问“谁是相对论的作者？”时，即使没有字面完全匹配，系统也能通过图谱关系找到“爱因斯坦”。
二、 感知记忆 (Perceptual Memory)
1. 是什么？

感知记忆主要用于处理和存储多模态数据，即人类感官能接收到的信息，包括文本、图像、音频等。它侧重于跨模态的理解和基于时间的瞬间记忆。

2. 是怎么做的？
  • 模态分离存储： 为文本、图像、音频创建独立的向量集合（Collection），避免维度不匹配，保证检索准确性。
  • 多模态编码器：
    • 文本使用 Text Embedder。
    • 图像使用 CLIP 模型。
    • 音频使用 CLAP 模型。
  • 检索流程 (Retrieve)：
    • 支持同模态（图搜图）和跨模态（文搜图）检索。
    • 时间衰减机制：引入“遗忘曲线”，使用指数衰减模型，24小时内分数较高，随时间推移权重降低。
    • 评分算法：
      • 公式：(向量相似度 × 0.8 + 时间近因性 × 0.2) × (0.8 + 重要性权重 × 0.4)。
      • 设计逻辑：主要看内容像不像（0.8），其次看是不是最近发生的（0.2），模拟人类对近期发生的事记得更清楚的特性。
3. 有什么用？
  • 多媒体处理：让AI不仅能读文字，还能“看”图、“听”音。
  • 跨模态搜索：用户可以用文字描述来搜索之前看过的图片或听过的声音。
  • 短期记忆模拟：优先回忆最近发生的感知细节（如刚才看到的东西），随时间推移逐渐“淡忘”不重要的细节。
4. 举个例子
场景：用户上传了一张“夕阳下的海滩”照片，并随后问道“我昨天傍晚看到了什么？”
  • 系统动作：
    • 存储时：使用CLIP模型将照片编码为向量存入图像集合，并记录时间戳。
    • 检索时：将用户的文字“昨天傍晚”解析为时间范围，将“看到了什么”转化为查询向量。
    • 排序：系统会找到那张照片，因为它的语义匹配度高（海滩 vs 看到什么）且时间近因性分值高（昨天刚发生），从而回答用户“你看到了一张夕阳下的海滩照片”。
总结对比
特性 语义记忆 (Semantic) 感知记忆 (Perceptual)
核心数据 抽象概念、规则、知识图谱 文本、图像、音频（多模态）
存储架构 图数据库 + 向量数据库 独立的向量集合（分模态）
关键技术 实体关系提取、混合检索 CLIP/CLAP编码、跨模态对齐
排序重点 语义相似度 (70%) + 图关系 (30%) 向量相似度 (80%) + 时间近因性 (20%)
模仿人类能力 思考、推理、联想 视觉/听觉感知、短期记忆遗忘

RAG系统

RAG，即检索、增强、生成，检索是指从知识库中查询相关内容；增强是将检索结果融入提示词，辅助模型生成；生成则输出兼具准确性与透明度的答案。

发展历程

  1. 第一阶段：朴素RAG（Naive RAG, 2020-2021）。这是RAG技术的萌芽阶段，其流程直接而简单，通常被称为“检索-读取”（Retrieve-Read）模式。检索方式：主要依赖传统的关键词匹配算法，如TF-IDF或BM25。这些方法计算词频和文档频率来评估相关性，对字面匹配效果好，但难以理解语义上的相似性。生成模式：将检索到的文档内容不加处理地直接拼接到提示词的上下文中，然后送给生成模型。
  2. 第二阶段：高级RAG（Advanced RAG, 2022-2023）。随着向量数据库和文本嵌入技术的成熟，RAG进入了快速发展阶段。研究者和开发者们在“检索”和“生成”的各个环节引入了大量优化技术。检索方式：转向基于稠密嵌入（Dense Embedding）的语义检索。通过将文本转换为高维向量，模型能够理解和匹配语义上的相似性，而不仅仅是关键词。生成模式：引入了很多优化技术，例如查询重写，文档分块，重排序等。
  3. 第三阶段：模块化RAG（Modular RAG, 2023-至今）。在高级RAG的基础上，现代RAG系统进一步向着模块化、自动化和智能化的方向发展。系统的各个部分被设计成可插拔、可组合的独立模块，以适应更多样化和复杂的应用场景。检索方式：如混合检索，多查询扩展，假设性文档嵌入等。生成模式：思维链推理，自我反思与修正等。

统一嵌入与向量存储

在前面分块的基础上，将分块内容转换为向量，然后进行存储

由于markdown格式的文本存在 标题#、粗体 *、链接 []()等符号，这对于语义理解来说通常是噪音，故这里使用 _preprocess_markdown_for_embedding，预处理分块的markdown文本，清除噪音

具体做了以下 6 项清理工作：

  1. 移除标题符号 (#)：
    • re.sub(r'^#{1,6}\s+', '', ...)
    • 去掉行首类似 ## 标题 中的 ## ，保留“标题”文字。
  2. 移除链接格式：
    • re.sub(r'\[([^\]]+)\]\([^)]+\)', r'\1', ...)
    • 将 [OpenAI](https://openai.com) 转换为 OpenAI，只保留显示文本。
  3. 移除强调标记（加粗、斜体、行内代码）：
    • 去除 **加粗**、*斜体* 和 代码 两侧的符号，只保留内部文字。
  4. 移除代码块包裹：
    • re.sub(r'```[^\n]*\n([\s\S]*?)```', r'\1', ...)
    • 移除代码块的开始和结束标记（```），保留代码块内的内容。
  5. 规范化换行：
    • re.sub(r'\n\s*\n', '\n\n', ...)
    • 将连续的多个空行合并为标准的双换行（段落分隔），避免因为空行过多影响分块。
  6. 压缩空白字符：
    • re.sub(r'[ \t]+', ' ', ...)
    • 将连续的空格或制表符替换为单个空格。

得到处理好后的分块文本后，按照batch_size，分批次使用嵌入模型对所有数据进行向量化处理

对生成的向量进行统一格式处理，确保最终格式为 List[List[float]]

高级检索策略

多查询扩展（MQE）

让ai生成同一问题的不同问法，然后再进行检索增强

假设文档嵌入（HyDE）

对问题进行初始尝试解答，然后用该解答进行检索（缩小语义距离）

扩展检索框架

hello-agents将上述两种方案进行整合，通过enable_mqe和enable_hyde参数让用户可以根据具体场景选择启用哪些策略：对于需要高召回率的场景可以同时启用两种策略，对于性能敏感的场景可以只使用基础检索。

扩展检索的核心机制是"扩展-检索-合并"三步流程。首先，系统根据原始查询生成多个扩展查询（包括MQE生成的多样化查询和HyDE生成的假设文档）；然后，对每个扩展查询并行执行向量检索，获取候选文档池；最后，通过去重和分数排序合并所有结果，返回最相关的top-k文档。这种设计的巧妙之处在于，它通过candidate_pool_multiplier参数（默认为4）扩大候选池，确保有足够的候选文档进行筛选，同时通过智能去重避免返回重复内容。

MQE擅长处理用词多样性问题，HyDE擅长处理语义鸿沟问题，而统一框架则确保了结果的质量和多样性。对于一般查询，建议启用MQE；对于专业领域查询，建议同时启用MQE和HyDE；对于性能敏感场景，可以只使用基础检索或仅启用MQE。

上下文工程

上下文工程关注的是“在每一次模型调用前，如何以可复用、可度量、可演进的方式，拼装并优化输入上下文”，从而提升正确性、鲁棒性与效率

其与提示工程的区别：

  1. 提示工程关注如何编写与组织 LLM 的指令以获得更优结果（例如系统提示的写法与结构化策略）；而上下文工程则是在推理阶段，如何策划与维护“最优的信息集合（tokens）”，其中不仅包含提示本身，还包含其他会进入上下文窗口的一切信息。
  2. 上下文工程可以看作是提示工程的进阶，不仅包括提示，也包括系统指令、工具、MCP（Model Context Protocol）、外部数据、消息历史等。

有效上下文

优秀的上下文工程目标是：用尽可能少、但高信号密度的 tokens，最大化获得期望结果的概率。

主要围绕以下三方面进行

  • 系统提示（System Prompt）：给出明确直白的信息提示
  • 工具（Tools）：工具职责明确单一、语义清晰、对错误鲁棒（出现错误有完整的错误信息）、参数描述明确
  • 示例（Few-shot）：为模型提供代表性好的示例

上下文检索与智能体式搜索

工程实践正在从“推理前一次性检索（embedding 检索）”逐步过渡到“及时（Just-in-time, JIT）上下文”。后者不再预先加载所有相关数据，而是维护轻量化引用（文件路径、存储查询、URL 等），在运行时通过工具动态加载所需数据。这样可让模型撰写针对性查询、缓存必要结果，并用诸如 head/tail 之类的命令分析大体量数据——无需把整块数据一次性塞入上下文。其认知模式更贴近人类：我们不会死记硬背全部信息，而是用文件系统、收件箱、书签等外部索引按需提取。

允许智能体自主导航与检索还能实现渐进式披露，从而减少token消耗

在实际实践中，可以采用一种混合策略。

根据对应的任务需求（动态性和时效性），先给予智能体少量高价值的上下文保证速度，然后令智能体按需加载更多的信息。（如可以预先放入类似“项目约定说明（如 README/指南）”的文件，同时提供 glob、grep 等原语，让智能体即时检索具体文件，从而绕开过时索引与复杂语法树的沉没成本）

1. 任务动态性 (Task Dynamism)

定义：

指的是任务所处的环境（如代码库、数据库、文档）发生变化的频率，以及任务本身的不确定性程度。

  • 低动态性：环境是静态的，信息很久没变过，或者任务路径非常明确。

  • 高动态性：环境正在被频繁修改（如正在开发的git分支），或者信息需要实时验证，预先建立的索引可能已经过时。

场景举例：

  • 场景 A：高动态性（正在狂改代码时）

    • 情况：你正在修改一个核心函数 process_data()，且刚保存了文件，还没提交 git，甚至还没跑编译。

    • 策略选择：此时如果你问智能体“现在的逻辑哪里有问题？”，前置加载的索引（如向量数据库或旧的语法树）是失效的，因为它们记录的是修改前的代码。

    • 智能体行为：必须依赖 glob/grep/cat 等工具去“即时读取”文件系统上的最新内容。

    • 结论：动态性高 →\rightarrow→ 减少依赖预存索引，增加智能体自主探索（实时读取）。

  • 场景 B：低动态性（阅读遗留项目或第三方库）

    • 情况：你想了解一个已经发布了半年的第三方库 axios 的基本用法。

    • 策略选择：代码库是静止的。

    • 智能体行为：可以直接把 README.md 或核心接口定义前置加载到上下文中。

    • 结论：动态性低 →\rightarrow→ 可以大量使用预加载的高价值文档，速度快且准确。

2. 时效要求 (Timeliness Requirements)

定义：

指的是用户或业务流程对智能体响应速度的容忍度。是需要“秒回”，还是允许智能体“慢工出细活”。

  • 高时效（低延迟）：用户在聊天框等着，希望立即看到思路或答案。

  • 低时效（高延迟）：后台任务、CI/CD 流水线分析、过夜的代码重构任务。

场景举例：

  • 场景 A：高时效（IDE 代码补全/对话助手）

    • 情况：你在写代码时卡住了，问 Copilot：“这个变量怎么定义？”

    • 策略选择：你等不起智能体去运行 10 次 grep 命令。

    • 智能体行为：必须前置加载当前文件和相关的引用文件片段。必须牺牲一部分全面性，换取速度。

    • 结论：时效要求高 →\rightarrow→ 增加前置加载（以此为准，猜错了也没办法，速度第一）。

  • 场景 B：低时效（全库代码审查/Refactoring）

    • 情况：你给智能体下达指令：“帮我检查整个项目中所有未处理的 Promise 异常，并生成报告。”

    • 策略选择：你不急着马上要结果，但要求不能漏掉任何一个文件。

    • 智能体行为：只前置加载一个 GUIDE.md（告诉它怎么做），然后让智能体自主探索，使用 glob 遍历成千上万个文件，慢慢 grep。

    • 结论：时效要求低 →\rightarrow→ 减少前置加载（只给指令），允许大量自主探索（换取精准度和覆盖面）。

面向长时程任务的上下文工程

主要针对一些长时间处理、会产生超出模型上下文窗口限制的任务，如大型代码库迁移

因此为了防止上下文的无限增长而无法涵盖所有上下文信息的情况，需要对上下文进行处理，常见的方式有：压缩整合（Compaction）、结构化笔记（Structured note-taking）与子代理架构（Sub-agent architectures）。

压缩整合

压缩整合

定义：当对话接近上下文上限时，对其进行高保真总结，并用该摘要重启一个新的上下文窗口，以维持长程连贯性。

实践：让模型压缩并保留架构性决策、未解决缺陷、实现细节，丢弃重复的工具输出与噪声；新窗口携带压缩摘要 + 最近少量高相关工件（如“最近访问的若干文件”）。

调参建议：先优化召回（确保不遗漏关键信息），再优化精确度（剔除冗余内容）；一种安全的“轻触式”压缩是对“深历史中的工具调用与结果”进行清理。

适合场景：长对话连续性的任务，强调上下文的“接力”。

场景：
主智能体正在调试后端 API，上下文已经积累了 50 轮对话。里面充满了大量的 ls 命令、报错日志、尝试修复失败的代码片段以及冗长的思考过程。此时 token 数量接近上限，模型开始“遗忘”最初的需求，或者因为上下文过长导致响应变慢。

执行过程：
系统触发压缩机制。它不会简单地切断旧历史，而是生成一个高保真摘要。

压缩前（原始上下文 - 充满噪声）：

用户：运行测试。
智能体：执行 pytest… 报错 ModuleNotFoundError… 尝试安装依赖… 再次报错… 尝试修改路径… 依然报错…
…（几千个 token 的调试垃圾）…

压缩后（新上下文窗口的内容）：

【系统摘要】：

  1. 当前任务：修复 POST /api/todos 接口的 500 错误。
  2. 已验证事实：数据库连接正常；依赖包 flask-cors 已安装。
  3. 未解决缺陷：单元测试 test_create_todo 失败，原因是导入路径配置错误。
  4. 尝试过的无效方案：直接修改 sys.path (已回滚)。
  5. 下一步计划：检查 .env 文件中的 PYTHONPATH 设置。

【保留的最近工件】：

  • 文件内容：backend/app.py (当前版本)
  • 文件内容：tests/test_api.py (当前版本)

效果：
新窗口只有几百个 token，但智能体清楚知道“刚才试过什么不行”以及“现在该干什么”，没有丢失关键状态，同时丢弃了数千 token 的无用报错日志。

结构化笔记

结构化笔记

定义：也称“智能体记忆”。智能体以固定频率将关键信息写入上下文外的持久化存储，在后续阶段按需拉回。

价值：以极低的上下文开销维持持久状态与依赖关系。例如维护 TODO 列表、项目 NOTES.md、关键结论/依赖/阻塞项的索引，跨数十次工具调用与多轮上下文重置仍能保持进度与一致性。

子代理架构

子代理架构

思想：由主代理负责高层规划与综合，多个专长子代理在“干净的上下文窗口”中各自深挖、调用工具并探索，最后仅回传凝练摘要（常见 1,000–2,000 tokens）。

好处：实现关注点分离。庞杂的搜索上下文留在子代理内部，主代理专注于整合与推理；适合需要并行探索的复杂研究/分析任务。

经验：公开的多智能体研究系统显示，该模式在复杂研究任务上相较单代理基线具有显著优势。

适合场景：复杂研究与分析，能从并行探索中获益。

场景：
用户要求：“请帮我调研一下目前市面上最好的三个 ORM 框架（SQLAlchemy, Peewee, Tortoise），并基于我们的项目需求选一个，然后开始写代码。”

执行过程：
如果单代理做这件事，它会先搜索 SQLAlchemy，读取大量文档，上下文满了；再搜 Peewee… 最后大概率会迷失在细节中，或者把 context 撑爆。
使用子代理架构：

  1. 主智能体（Manager）：
    • 指令：规划任务。启动三个“研究员”子代理。
    • 状态：上下文非常干净，只包含用户需求。
  2. 子智能体 A（SQLAlchemy 专家）：
    • 环境：独立的上下文窗口。
    • 行为：疯狂搜索、阅读几十页文档、查看 StackOverflow 对比性能。上下文非常乱。
    • 产出：向主智能体汇报一段 200 字摘要：“SQLAlchemy 功能最全，生态最好，但学习曲线陡峭。适合大型项目。” -> 然后销毁该上下文。
  3. 子智能体 B（Peewee 专家） & 子智能体 C（Tortoise 专家）：
    • 并行做同样的事，各自产生摘要。
  4. 主智能体（Manager）：
    • 接收：收到三份精简摘要（共约 600 tokens）。
    • 决策：结合项目是“小型 To-Do 应用”，决定选择 Peewee（因为它轻量）。
    • 行动：开始写代码。

效果：
主智能体从未看到那几百页的文档和杂乱的搜索结果，它的思维保持清晰且聚焦于决策。繁重的“阅读理解”工作被分摊到了临时的子代理中，用完即焚。

它以 Markdown 文件作为载体，头部使用 YAML 前置元数据记录关键信息，正文用于记录状态、结论、阻塞与行动项等内容。

为什么需要？

  • 当处理一个长耗时任务时，智能体可以通过该设计存储当前任务的进度
  • 轻量，不需要与数据库交互

hello-agents实现了 NoteTool

存储格式

  1. 笔记格式
    由 YAML + Markdown 格式组成
  1. 索引文件
    json格式

核心操作

创建

读取传入参数的标题 title、内容 content、笔记类型 note_type、标签 tags

如果 title 或者 content 为空，则报错

如果 note_type 为空，则设置默认值 general

如果 tags 为空，则设置默认值空列表 []

之后分别创建md内容和json索引，保存至硬盘中（写文件）

读取

根据传入的笔记id note_id

获取笔记路径，读取返回

更新

根据更新类型，更新对应的参数字段和更新时间，最后写入文件和更新索引

删除

根据提供的笔记id note_id

删除对应文件和索引里的数据

列出

遍历内部存储的索引，然后组织返回

搜索

根据输入 query，查找标题、内容、标签是否包含，然后返回

即时文件系统访问

即提供调用命令的工具

hello-agents只针对linux系统进行了实现，需要针对windows系统进行适配
